## Goal
Users can add new equipment to a case's network from the case editor's element table (Nodes / Branches / Appliances
tabs), edit it like any other element, delete it again, run the case, and see the new elements in all result views.
The network file is never changed: additions are case data, frozen into each run like `network_overrides`.
Phase 2 (T32, later, not now) adds the same elements by drawing on the diagram; design the data model and the add
form so T32 can reuse them (see "Phase 2 hooks").

## Scope
Addable components: `node`, `line`, `link`, `sym_load`, `sym_gen`, `shunt`. Not in scope: transformers (3-winding
and 2-winding), sources, asym components, deleting elements that come from the network file (they can already be
switched out of service). Mention these in the report so the orchestrator can file deferred issues.

## Data model (backend, `models.py`)
- New `NetworkAddition` model: `component` (one of the addable components), `id: int`, `name: str` (min length 1),
  `attrs: dict[str, float]` (PGM input attributes in SI units; node refs as ids; booleans 0/1), and an optional
  `position: {x: float, y: float} | None` (diagram placement, unused in phase 1 but stored and returned as-is).
- `CaseStudy.network_additions: list[NetworkAddition] = []` ("New elements on top of the unchanged network file").
- An extension-point module `backend/src/gridsim/networks/addable.py`, in the style of `editable.py`: per addable
  component, the list of fields the add form shows (reuse `EditableField` or a sibling model with `required`,
  `default`, `kind` incl. a `node` ref kind), plus PGM attributes that are filled automatically (e.g. `from_status` /
  `to_status` = 1, `status` = 1, `type` for loads/gens = const_power, line `tan1` = 0 / `r0,x0,c0,tan0` copied from
  the positive sequence where PGM needs them for power flow — check what PGM's `validate_input_data` requires for
  sym power flow and fill only that). Sensible defaults: line R1/X1/C1/I_n from typical MV cable values; node
  `u_rated` from the form (the UI prefills it from the node the user connects to, or the most common u_rated).
  Expose it at `GET /api/networks/addable-fields` (like `editable-fields`).

## Applying additions
- New `networks/additions.py` (or extend overrides.py if cleaner): `check_additions(net, additions)` and
  `apply_additions(net, additions) -> LoadedNetwork`. Append rows to copies of the PGM input arrays
  (`power_grid_model.initialize_array`), creating a component array if the network has none of that kind. Add names
  to `names`, rebuild the topology with `build_topology`.
- Order: additions first, then overrides. Overrides on added elements are allowed (the table edits them through the
  normal override path) — so `check_overrides` must see the post-addition network.
- Validation messages (as `ValidationIssue` errors, with element names): duplicate id, id clashing with any existing
  PGM id (ids are unique across all components), unknown component, missing required attr, node reference to a
  node that exists neither in the file nor in the additions, a line/link with from == to, a link between nodes of
  different `u_rated` (warning or error — follow PGM), non-finite values, then PGM `validate_input_data` on the result
  like `check_overrides` does.
- Call sites: `validation.py` and `studies/timeseries_powerflow.py` (both currently call `apply_overrides`). Results
  (summary names, snapshots, timeseries, violations) must show added elements by their names. Profile assignments
  with `ids: null` (all loads/gens) naturally include added ones — keep that, and make sure targeted `ids` may refer
  to added elements.
- API: update `docs/api-contract.md` (CaseStudy field, new endpoint), run `make types`, fix `frontend/src/api/schema.ts`.

## Frontend (case editor, element table)
- `components/network/overrides.ts` `effectiveTopology` (or a new `additions.ts` beside it, with unit tests) mirrors
  the backend: the effective topology includes added elements (marked as added), so the table, the diagram (it will
  simply lay them out automatically in phase 1) and the details panel show them.
- Each table tab gets an **Add** button (`Add node`, `Add branch`, `Add appliance`). It opens a dialog/form:
  component type (for branches: line / link; appliances: load / generator / shunt), name (prefilled unique, e.g.
  `New line 1`), node selectors (searchable by name; added nodes included), and the type's fields with units and
  defaults from `addable-fields`. Prefill sensible values: node `u_rated` = the most common u_rated in the network;
  line parameters from the add-field defaults. Validate inline (required, numbers, from ≠ to), and on Save append a
  `NetworkAddition` with a fresh id = 1 + max id over the file topology and existing additions.
- Added rows show a clear `New` badge, are counted in the change counts / "Changed only" filter, are editable through
  the existing cells (they become overrides on the added id or — simpler and preferred — edits that update the
  addition's own `attrs`; pick one, document it, and keep "revert" semantics sensible), and have a **Delete** action
  (confirm). Deleting an added node that other additions reference must either be blocked with a clear message or
  delete the dependents after confirmation listing them — your call, document it. File elements cannot be deleted.
- The case's unsaved-changes / save flow and the case validation display must cover additions (server issues shown
  like override issues).
- Results views need no special work beyond showing names; verify the snapshot and violations show an added load.
