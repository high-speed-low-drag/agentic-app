Requested by the user on 2026-10-26. The current `project.md` (T22) "misses the mark": it describes **how** to build
GridSim (stack versions, file layout, code, stylesheet tables, agentic workflow). The user wants it to describe **what**
app and features need to be built, so another agent can build the same product with its own technical choices.

Rewrite `project.md` in place, at the repo root. Do not change any app code. Do not git commit; the orchestrator does
that. Keep `.agent/progress/T23.md` updated, and **write `project.md` section by section**, saving each section and

## What to keep and what to drop
Write it as a product requirements document.
- **Keep** everything a user can see or rely on:
  - features, workflows, screens and their contents;
  - behaviour rules, defaults, limits, units, labels and messages that matter;
  - domain semantics (how profiles, scale vs add, factor, overrides and limits affect the study);
  - what results are computed and how they are defined: KPIs, violation episodes, extremes, envelope, heatmap
    aggregation, energised vs not;
  - visual meaning: what each colour, symbol and cue communicates, with the default colour choices stated as design
    intent, e.g. "overvoltage red, undervoltage blue, neutral grey band";
  - non-functional requirements (performance targets, reproducibility, persistence, light/dark, responsive widths, accessibility basics).
- **State only these as fixed constraints,** in one short section:
  - it's a local web app;
  - power flow uses the open-source power-grid-model engine, so there's no other solver;
  - the runtime is deterministic, with no AI/LLM features in the app;
  - the bundled sample networks (Vision MV validation network and IEEE 14 from PGM's test data, MPL-2.0 attribution);
  - a future database/lakehouse network source must be possible, so network sources are pluggable as a product capability.
- **Drop:**
  - the tech stack and versions;
  - repo layout, module and file names, make targets and CLI internals;
  - code snippets, the stylesheet tables, exact CSS tokens and hex values (describe colours by meaning, giving a hex
    only where it truly defines intent);
  - internal APIs (an "HTTP API" section isn't needed: describe the data the product handles, not endpoints);
  - the test-hook names, CI workflow, agentic build workflow, ledger and briefs, and the appendix of inlined JSON.
- **Algorithms:** describe them as precise behaviour, in words, short formulas or tables: what the user gets, e.g.
  "the PV profile follows clear-sky sun elevation for the date and latitude, reduced by cloudiness". Don't give
  implementation code. Keep formulas where they define results the user depends on, such as loading = max(|S_from|, |S_to|) / rating.

## Required structure
1. **Product overview:** what GridSim is, who it's for, and the core journey (define a case → run → explore results).
2. **Fixed constraints** (the short list above).
3. **Concepts and glossary:** network, case study, time window, profile assignment, scale/add/factor, equipment
   override, run (frozen copy), limits, violation episode, extremes, energised, display settings vs study data.
4. **Features,** one subsection each. For each feature give a user story, the requirements as numbered, testable
   statements, defaults and edge cases, and **acceptance criteria** as Given/When/Then or checklists:
   - cases list (create, open, delete with confirm, last-run status);
   - network selection and upload (samples, upload of a PGM JSON file, validation);
   - network explorer: diagram with electrical symbols; element tables by type; selection details; diagram ↔ table
     behaviour (a quiet select, and "Edit in table" jumps); zoom by buttons only;
   - equipment parameter editing: in-cell editing; which parameters are editable per equipment type, with units;
     changed cues, revert, Changed-only, Revert all; network switch clears edits; missing file values shown as "not set";
   - time and calculation settings (customisable window and resolution, presets, timestep count, solver options, limits);
   - profiles: generators and their parameters; JSON-schema-driven forms as a requirement ("each generator declares its
     parameters; the editor renders them"); scale/add/factor; targeting all or selected elements; preview; CSV upload;
     edited equipment values reflected in the target list;
   - validation (errors vs warnings, messages);
   - running (progress, cancel, failed timesteps, frozen copy, performance target);
   - results summary and KPIs;
   - each result view: voltage envelope, element time series, loading heatmap, violations and extremes (explain the
     difference), network snapshot;
   - network snapshot details: playback speeds 1×–16× with no skipped frames; the 24 h day/night clock; the
     daylight-shaded slider; the user-defined four-point voltage colour scale (saved per browser); the loading colours;
   - visual status cues in both diagrams: out of service, not energised, within band, edited;
   - charts: limit lines always visible and labelled.
5. **Non-functional requirements:** performance (e.g. 1-year 15-min on Vision MV in a few seconds; snapshot playback
   at 16× about 25 steps/s), persistence, reproducibility, theming, responsiveness, keyboard and accessibility basics, error handling.
6. **Data handled:** inputs, outputs and persisted entities, described conceptually (what is stored per case and per
   run, what the results contain), without file formats unless they are user-facing (PGM JSON upload, CSV profiles).
7. **Out of scope and future work:** deferred issues #1–#5 as short items, plus known product caveats (IEEE 14 has no
   branch ratings; PV in scale mode on loads multiplies demand; voltage regulators aren't shown).
