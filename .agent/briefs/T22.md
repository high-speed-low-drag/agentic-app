Requested by the user on 2026-10-26. The deliverable is a single Markdown file at the repo root, `project.md`, that
the user can hand to another coding agent. That agent, with **no access to this repo or conversation**, must be able
to rebuild every existing feature to the same behaviour. Do not change any app code. Do not git commit; the
orchestrator does that. Keep `.agent/progress/T22.md` updated after every sub-step: a checklist, sections done, and a
precise `Next step:` line. If that file exists, continue from it.

## Required structure of `project.md`
Write it as a build spec, not a history: imperative, precise, with exact numbers. Start with a short table of contents.
1. **Purpose and principles:** a deterministic runtime with no LLM in the app; built and extended with agentic coding;
   time series as a PGM batch; per-case overrides on top of an unchanged network file; display settings vs study data.
2. **Tech stack with exact versions,** from the lockfiles and manifests: Python, uv, power-grid-model, FastAPI, pydantic,
   pandas, pyarrow; Node, React, TS, Vite, Tailwind, react-router, react-query, ECharts, Cytoscape and extensions,
   Vitest, Playwright, ESLint, ruff.
3. **Repository layout,** a tree with a one-line purpose per module, plus the commands (`make install`, `dev`, `check`,
   `e2e`, `types`, `ci-install`, and the CLI).
4. **Domain model and storage:** every Pydantic model with its fields, types, defaults and validation rules (CaseStudy,
   TimeSettings, CalculationSettings, Limits, ProfileAssignment including `factor`, NetworkOverride, RunInfo,
   ResultSummary and so on); the workspace file layout; the demo case seed.
5. **HTTP API:** the complete contract. Inline it fully, including later additions: editable-fields, `params` with
   `null`, `b1` on shunts, the frozen run case, error-code conventions and SSE events.
6. **Engine and algorithms,** precise enough to reimplement:
   - batch building (scale/add, `factor`, assignment order, overrides first);
   - chunked `calculate_power_flow` with progress, cancel and failed timesteps;
   - every profile generator's formula and parameters, including the PV solar geometry;
   - the results summary: KPIs, energy and losses, contiguous violation episodes and the cap;
   - the timeseries, envelope, heatmap bucketing and snapshot queries;
   - editable-fields registry contents and units;
   - override validation messages;
   - NaN to null handling.
7. **Frontend spec, page by page:**
   - app shell;
   - cases list;
   - case editor tabs: network explorer with the diagram, table, in-cell editing, changed cues, click-to-row and
     Edit-in-table behaviour, Changed-only and Revert all, and network switch confirm; time and calculation;
     profiles with the JSON-schema form, preview, CSV upload, scale factor and effective-value markers;
   - the run page with SSE and polling fallback;
   - the runs list;
   - the results page with KPI tiles and every result view in the registry.
8. **Network diagram spec:**
   - layout choices;
   - node and element styling: exact sizes (9 px nodes, 11 px when changed, a 14 px hit area and the nearest-node
     fallback), colours and tokens;
   - IEC symbols (transformer two-circle, three-winding, generator ~, external grid, capacitor/reactor/shunt by b1)
     and how overlay symbols are placed and rotated;
   - the out-of-service and not-energised styles, and the BFS for energised nodes;
   - changed and selected cues, the "off" label, and the legend;
   - zoom: buttons only, no wheel;
   - theme regeneration;
   - test hooks such as `window.__gridsimCy` and the data attributes.
9. **Results snapshot spec:**
   - playback speeds (base 600 ms, ×1–16), prefetching and the never-skip timing;
   - the four-point voltage colour scale: the colour maths with its 28 % starting tint, the defaults, validation,
     the localStorage key and the popover;
   - the loading colour scale;
   - the 24 h clock: solar formula, latitude source, dial and badge;
   - the daylight-shaded slider (31-day rule);
   - the clock/legend corner layout.
10. **Charts:** limit lines are always visible (the axis-range helper and label formats); dataZoom.
11. **Design tokens:** all CSS custom properties with their light and dark values, as used, plus number and unit
    formatting rules.
12. **Testing spec:**
    - what `make check` and `make e2e` run;
    - Playwright config: ports 8100/5180, temp workspace, CI retries;
    - for each feature, the acceptance tests to write, mirroring the existing e2e and unit tests by behaviour;
    - the contract drift guards (committed `openapi.json`, `contract.check.ts`).
13. **CI:** the GitHub Actions workflow as specified.
14. **Agentic build workflow for the rebuilding agent:** ledger, briefs, progress journals, checkpoint commits with
    explicit paths, the done-check rule, the resume protocol and session-start hook, the go-ahead gate, and
    implementation done in sub-agents. Then a **recommended build order** as a task list (like T1–T21 regrouped into
    sensible milestones), each with a done check.
15. **Known pitfalls and decisions:**
    - IEEE 14 has no branch ratings, so loading is 0;
    - generic branches;
    - voltage regulators are attached to generators, not branches;
    - PV in scale mode on loads multiplies demand;
    - Cytoscape ignores overlay-padding for hit testing;
    - wheel zoom swallowing the page scroll;
    - the `<main>` scroll container;
    - the theme-dependent neutral colour;
    - `npm ci` vs `install`;
    - never `git commit -a` while agents are running;
    - sample-network attribution (MPL-2.0).
16. **Deferred backlog:** issues #1–#5, each with its proposed fix, marked as not part of the rebuild unless asked.

## Quality bar
- It must be self-contained: no "see file X". Inline the needed content. It may say where a file lives in the target layout.
- It must be complete: every user-visible feature and every API route exists in it. Before finishing, cross-check by
  listing `frontend/src/results/views/index.ts` entries, all API routes (`grep -rn "@router" backend/src`), all
  e2e spec files, and the editable-fields registry, and confirm each appears in `project.md`.
- Exact numbers and strings where behaviour depends on them: limits, defaults, sizes, colours, labels and messages
  that tests assert.
- Length: as long as needed, likely 1,500–3,000 lines. Use headings, tables and code blocks for schemas.
- Exclude secrets, local absolute paths, and the user's email.

Report back concisely:
- the path;
- the line count;
- the section list;
- anything you couldn't determine, and where the code and briefs disagreed (and which you followed).
